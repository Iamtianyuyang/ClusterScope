2. 无 root 合规（2026-10-07 增补：23 条 NR-* + M10 不变量）

需求原文：「这个项目是要做一个不用 root 的程序」。上一版只把「无 root」当成一条文档不符（DOC-21）记录。 这次增补把它变成 23 条可判定约束（NR-01…NR-21、NR-06b、MRG-02；合计 104 条）， 在真实 release 二进制上逐条复跑（uid 3000、无 sudo），并在合流方案里加了 M10 不变量 NRM1–NRM8。 逐条判定与命令见 report/merge-plan.md 的 M10；原始证据在 qa/evidence/no-root-verify*.txt 与 qa/qa-report.json 的 Q300–Q330。

一句话结论：运行时确实不需要 root（实测），但交付面自相矛盾——仓库发的部署件要 root、README 写的管理命令在干净机器上没有对应的 unit、无 root 的数据库路径一处未写。

核心结论（原样传达，不软化）

  1. ✅ 运行时确实不需要 root：uid 3000、CapEff=0000000000000000、零 HOME 外写入； server（8080/50051 监听、/api/health=200）、agent（起得来并上报）、TUI（pty 正常渲染）全功能可用； /proc 权限不足时按 README 承诺降级；两个端口都 >1024，不需要 CAP_NET_BIND_SERVICE。
  2. ❌ 部署件与承诺自相矛盾：随仓库发的 deploy/server.service、deploy/agent.service 是 系统级 unit（User=clusterscope、/usr/local/bin、/etc/clusterscope、 /var/lib/clusterscope、/var/log/…、WantedBy=multi-user.target），非 root 实测装不上 （systemctl link → Interactive authentication required；cp → Permission denied）； 而 README 通篇写 systemctl --user。
  3. ❌ 仓库里 0 个用户级 server unit：README:288-289 的 systemctl --user restart clusterscope-server 在干净机器上必然失败（本机那份 ~/.config/systemd/user/clusterscope-server.service 是手写私货， 2026-08-10 建立、当前 disabled/inactive，不属于仓库）。
  4. ❌ 无 root 的数据库路径未文档化：README:57/87 承诺「无 root 时可用 docker compose up」， 但本机无 docker、podman 零镜像且无外网 → 该承诺在本环境不可执行；真正可行的路径（源码编译 PostgreSQL 16.4 到 HOME） README 0 处记载。

边界与诚实项（都要写进部署前提）

  • ⚠️ linger 是每机配置（双向记录）：本机当前 Linger=yes（loginctl show-user tianyuyang → Linger=yes、State=active）， 用户级服务活过登出——本机实测 ✅（探针 unit 的 MainPID 在会话结束后仍存活；更强的证据是自 2026-09-02 起常驻的用户级 agent，PID 266643，跨过了每一次登出）。 但本机这个 yes 很可能是 Leader 前期探测时执行 loginctl enable-linger 造成的，不是集群默认值（探测初期读到的是 no）。 反向语义：linger=no 的节点上，最后一个会话结束时 logind 会停掉该用户的 per-user manager，所有 unit 一起死 → 干净节点上用户级 agent 会随登出而死，而开启 linger 通常需要管理员/root → 这是「无 root 承诺」的一条边界。 该分支在本机无法复现（无 root、不许改集群配置），只作语义记录，不替集群做假设。
  • ⚠️ 作者 harness 的 NR6 PASS 是假阳性：qa/harness/no-root-checks.sh:171-177 用 grep -q 'ClusterScope Agent starting' 判 NR6、从不读进程退出码，而问候行在崩溃之前就打印了 → 进程其实已经死了，检查却 PASS。NR-06 的最终判定以第 5 阶段为准（Q305：violated，复现出 exit=1）。
  • ⚠️ 诚实项：NRM5 的 grep 模式在 GNU grep 下匹配空集（qa/merge-plan-requirements.md 里写成 grep -E "setuid\|setgid\|…"，ERE 里 \| 是字面竖线不是「或」）——它的「0 命中」是模式假象。 用正确的模式复跑命中 2 行：crates/agent/src/job_executor.rs:128-129 的 cmd.pre_exec(|| libc::setsid())，用途是给子进程建新会话/进程组（配合取消时按进程组 kill），不是提权。 结论（无特权原语）不变，已作为 discovery N14 原样并入。
