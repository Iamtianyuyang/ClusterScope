Bug ① 最后管理员守卫从未运行

症状SELECT COUNT(*) … FOR UPDATE 被 PostgreSQL 逐字拒绝（聚合 + 行锁在 PG 里不合法），于是「最后一个启用管理员不得被停用/降级/删除」这条守卫一次都没跑到：请求在 SQL 层就报错，守卫的 400 分支是死代码。
为什么测试才咬得到编译期完全合法；单元测试用的假事务不校验 SQL；只有连真 PG 才炸。
QA 独立复现qa/evidence/m6-qa5-last-admin-guard.txt：在专属库 clusterscope_qa5_guard 上跑「拒绝路径」——PATCH enabled=false → 400、PATCH role=viewer → 400、DELETE → 400，三次拒绝后 DB 仍是 admin:admin:enabled=true；再建第二个 admin，守卫立刻放行（降级 → 200），删掉唯一管理员仍是 400。
现状态已修（合流提交里改成先锁行再计数）。注意：这条守卫的自动化判据在规格阶段被移出（共享库里无法构造「只剩一个启用管理员」的前置），改由 QA 在专属库上人工核验 —— 记录在 qa/merge-m6.qa.md 与 qa/mrg6-errata.json，不是静默跳过。

Bug ② 读错 /proc/<pid>/stat 下标 → 取消路径从不发信号

症状process_starttime() 取的是 /proc/<pid>/stat 的下标 20，那其实是 vsize（虚拟内存字节数），不是 starttime（下标 19）。于是「进程是否被回收」的比对必然不等 → 走「pid 已被回收」分支 → 取消任务时永远不发 SIGTERM/SIGKILL。
为什么测试才咬得到只在 Linux 真进程上错，且 vsize 在两次采样之间只要进程分配过内存就会变——单测里跑得快反而可能碰巧相等。
QA 独立复现qa/evidence/m6-qa5-cancel-e2e.txt（I/J 段）：
I 段：同一 pid 同时读三个值 —— 下标 19 = 375446910（÷CLK_TCK 后正是「存活 ~0s 的启动时刻」，与 ps etimes 对得上）、下标 20 = 226271232（÷1024 = 220968 kB，与 /proc/<pid>/status 的 VmSize 逐字节相同）。
J 段：连续 4 次采样，下标 20 从 233541632 → 434880512 一路随分配变化，下标 19 全程不变 —— 结论行：「只要作业进程在 spawn 与取消之间分配过内存，比较就必然不等 → 走 pid-recycled 分支 → 不发信号。」
现状态已修。修复后 SIGTERM ignored / Forced cancellation 两条日志都能在 demo 14 里看到。

Bug ③ 路由重复注册 → 启动即 panic

症状把 B 的 handlers.rs 与 main.rs graft 进主线后，/audit-logs 被注册两次（admin_routes 与 read_routes 各一次，两个 Router 之后 merge 到一起）→ axum 0.7 在启动时直接 panic。
为什么测试才咬得到能编译、能过单测（单测不起真的 Router）；只有把 server 真启一次才炸。
QA 独立复现qa/evidence/m6-qa5-route-dup.txt：

这三个 bug 的意义：如果只做「整文件覆盖式合并」或只看编译过不过，它们会原样进主线 —— ① 让一条安全守卫变成死代码，② 让「取消任务」这个核心功能静默失效，③ 让 server 直接起不来。合流的价值恰恰在于：把 B 的代码放进主线的测试与真实运行里，让它们自己暴露出来。
